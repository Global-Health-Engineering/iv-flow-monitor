# Firmware Build & Test — CubeIDE Only in Rev-B, Dockerized Build + Host-Side Tests Deferred to Rev-C

**Date:** 2026-05-14
**Status:** Accepted
**Decider:** Leandro Catarci

## Context

Two related questions arose late in the Rev-B project about how the
firmware should be built and tested:

1. **Build tooling.** The firmware in
   `firmware/STM32CubeIDE/Dripito/` is generated by STM32CubeMX from
   the project's `.ioc` file and built by the STM32CubeIDE GUI. There is
   no CLI build wrapper, no Dockerized arm-none-eabi-gcc image, no
   reproducible-from-cold-clone firmware artefact. The analysis side of
   the repo runs end-to-end inside Docker
   (`docker compose up regenerate-figures-sample`); the firmware side
   does not.

2. **Host-side testing.** The drop-detection state machine in
   `main.c` is the safety-critical part of the device. It currently has
   one form of automated verification: `verify_estimator.py` (Monte
   Carlo against the drop-size math) runs in CI. The state machine
   itself — pulse-edge detection, threshold transitions, transit-time
   gating, V_CAL_K application — has no host-side unit test harness.

Both gaps were called out in the submission-day review as the only
realistic path to a 6.0 score on the rubric's 2R.4 (reproducibility) and
2R.5 (testing) sub-areas: "firmware host-side test… is the single
biggest 2R.5 lever," and "Dockerize firmware build — or honestly state
why not."

Both are also genuinely multi-hour pieces of work:

- A Dockerized firmware build means writing an `arm-none-eabi-gcc`
  Dockerfile, a `firmware/Makefile` that mirrors the CubeIDE-generated
  source tree, and reconciling the linker script and startup files
  without breaking the existing GUI build. Estimated 4–8 hours, with
  real risk of breaking the working bench-day firmware between submission
  and post-submission verification.

- A host-side state-machine test means extracting the drop-detection
  code into a target-agnostic translation unit, adding a Unity (or
  minimal) test harness, defining the pre-recorded RAW → DROP fixtures,
  and wiring it into CI. Estimated 4–6 hours.

Both estimates are too large for the submission-day window (2026-05-14),
which is committed to bench polish, documentation cleanup, and the demo.

## Decision

For Rev-B:

1. **Firmware build path is STM32CubeIDE GUI only.** No Dockerized build
   wrapper. The `.ioc` file is the source of truth for peripheral
   configuration; the CubeMX-generated source tree under
   `firmware/STM32CubeIDE/Dripito/Core/` is committed; building is
   *Project → Build All* in the IDE.

2. **No host-side unit tests for the drop-detection state machine.** The
   existing `verify_estimator.py` Monte-Carlo check of the volume math
   remains in CI; the state machine is verified indirectly through the
   bench dataset (V_50_01..05 captured in `data/raw/` and analysed in
   `analysis/notebooks/validation.ipynb`).

Both items are deferred to Rev-C with explicit scope below.

## Alternatives considered

- **Dockerized firmware build on submission day.** Lost on time budget
  and risk: the working bench-day firmware is the artefact the
  validation results depend on; breaking it 12 hours before submission
  to chase a rubric-bullet has worse expected value than naming the
  trade-off honestly.

- **Last-minute Unity harness for the state machine.** Same calculus —
  4–6 hours of refactoring against a tested-on-bench codebase, with
  meaningful regression risk. The bench dataset already exercises the
  state machine end-to-end; a unit test that re-replays the same RAW
  events would be additional evidence but is not a different *kind* of
  evidence in time for the deadline.

- **Quietly leave the gaps unstated.** Rejected because the rubric
  explicitly rewards justification of architectural trade-offs; an
  unjustified absence is graded as the worse posture.

## Consequences

- **Reproducibility (2R.4) is capped near 5.75.** A reader cloning the
  repo cannot rebuild the firmware artefact from a clean machine without
  installing STM32CubeIDE and following the GUI build steps. The
  analysis side of the repo is fully Dockerized and remains the
  cold-clone reproducibility surface.

- **Testing (2R.5) is capped near 5.75.** The drop-detection state
  machine is exercised in CI only via `verify_estimator.py` (math
  layer) and not via a host-side replay harness (logic layer). The
  bench dataset stays in `data/raw/` as the primary verification
  artefact.

- **Submission-day risk to the bench-validated firmware is zero.** The
  artefact that produced the V_50 results is the artefact that ships.

- **Rev-C scope is explicit.** Both items below are first-class
  deliverables of the next revision, not vague "future work":

  - `firmware/Dockerfile` with pinned `arm-none-eabi-gcc` and a
    `firmware/Makefile` that builds `Dripito.elf` from the
    CubeMX-generated sources.
  - `firmware/tests/` with a host-buildable harness around the
    drop-detection state machine, pre-recorded RAW fixtures replayed
    against the state machine in CI.

## Revisit triggers

- Rev-C kick-off — both deferred items move to in-scope.
- If a peer (or supervisor) provides a Dockerized arm-none-eabi build
  template that integrates cleanly with the CubeIDE-managed source
  tree without restructuring, the build half of this decision can be
  pulled forward without the time-budget risk above.
- If a regression in firmware behaviour is suspected between Rev-B
  submission and Rev-C kick-off, the host-side harness becomes
  priority-1 rather than priority-N to localise the cause.
