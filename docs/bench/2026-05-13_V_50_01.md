```

```

The scale stream is new for this campaign — `tools/log_scale.py` exposes the Mettler-Toledo MS-series SICS `SIR` (Send Immediate, Repeatedly) command over the balance's USB-CDC virtual COM port. The stream's 23 Hz sampling captures ~46 samples per drop landing event at the 0.5 Hz drip rate observed in this run, so per-drop mass increments could be reconstructed in post-processing if needed. For this run the per-run total-mass gravimetric is used (the design that `analysis/notebooks/validation.ipynb` consumes).

## Raw observations

- 65 DROP rows captured (drop_N range 219..282; firmware uptime started before the bench).
- Mean transit `dt = 13107 µs` ⇒ v_TOP ≈ 0.711 m/s (gravity-corrected; consistent with free-fall from ≈ 25–30 mm above the TOP beam).
- Mean `pulse_top_us = 3941`, `pulse_bot_us = 8278`. **TOP-to-BOT pulse ratio ≈ 0.48** (BOT/TOP ratio ≈ 2.09×) — a load-bearing finding; see §"Findings" below and `docs/limitations.md` §3.
- Firmware V (V_50_01 era, TOP-only chord, no `V_CAL_K`) ≈ 13 µL/drop. The gravity-corrected mean-of-pulses model (now in both `load_run.py` and the final firmware) recovers ≈ 45.95 µL/drop uncalibrated, or **58.35 µL/drop after `V_CAL_K = 1.27`**.

## Findings

### 1. TOP-vs-BOT optical asymmetry (the dominant Rev-C lever)

The BOT photodiode reports a pulse ≈ 2× the TOP pulse for the same drop crossing both beams (BOT/TOP ratio ≈ 2.09× here). Physics expects 0.92× (drop is 9 % faster at BOT due to gravity, so its chord at BOT should be shorter, not longer). The 2026-05-13 backsplash falsifiability test showed the BOT extension is partially splash-driven (BOT/TOP fell to ≈ 1.13× when the device was repositioned higher on the chamber) and partially intrinsic sensor asymmetry. See `docs/limitations.md` §3 for the full treatment.

The mean-of-pulses approach (now in both `load_run.py` and the final firmware) partially absorbs this (BOT over, TOP under → mean roughly tracks truth). `V_CAL_K = 1.27` absorbs the residual on the run-mean. The per-drop residual (drop-shape oscillation between oblate and prolate during free fall) remains as ±30 % of `V_true` across the calibration runs.

### 2. Threshold-crossing requires a near-saturation baseline

At first boot today the TOP baseline calibration captured a baseline of ~3830 ADC units (vs the 2026-05-08 spec'd ~3100). With the original `CAL_MARGIN_HIGH = 220` this put `thresh_high = 4049`, only 45 units below ADC ceiling (4094). Drops could not reliably push TOP above threshold and the firmware emitted 0 DROP events while drips were falling. Dropping `CAL_MARGIN_HIGH` to 100 and `CAL_MARGIN_LOW` to 30 restored detection; see firmware diff for the full constants table.

### 3. Tilt sensitivity (qualitative)

The bench observed that small device-attitude changes cause drops to miss the beams entirely (DROP events go to zero). Once Leandro repositioned the chamber the TOP pulse extended from 1.5 ms to 3.1 ms — a 2× improvement from a sub-mm reposition. Captured in `D:\Obsidian\Dripito\01 Projects\Dripito Monitor\Logs\Bench Findings 2026-05-13.md` §5 for the verticality budget in the Rev-C chamber-holder revisit.

### 4. The architecture is sound; the optical front-end and oscillation-aware model are the Rev-C levers

The dual-beam time-of-flight is velocity-invariant by construction and the intra-run per-drop CV matches the a priori prediction. The per-run scalar bias (this run's `k_pre = 1.61`) is partly attributable to the TOP-vs-BOT asymmetry — a Rev-C optical front-end with matched LED currents, identical optical apertures, and BOT beam moved further from the pool would close most of this gap — and partly to drop-shape oscillation that the chord-time architecture cannot resolve per-drop (see `docs/limitations.md` §1). Two horizontally-separated beam pairs would let firmware infer the oscillation phase.

## Reproducing this run

The capture and analysis chain is:

```powershell
# Capture (run concurrently)
python tools\log_uart_run.py capture --port COM3 --rate 50 --run V_50_01 --duration 200 --force
# scale streamer (inline SIR loop; will be wrapped into a `log_scale.py stream` subcommand
# in a follow-up commit)

# Analyse
python tools\build_bench_overlay.py \
  --device-csv data\raw\2026-05-13_macro20_50mlh_01_board1.csv \
  --scale-csv data\raw\2026-05-13_macro20_50mlh_01_board1_scale.csv \
  --beam-mm 10.2 --density 1.000 --rate-mlh 50
```

Output is byte-identical given the same input CSVs (RNG seed is the bench date, fixed in `analysis/scripts/error_budget.py`).
